# RC gate execution plan — Pass 27

This is the operational handoff for all seven mandatory release gates. It is not approval to run privileged or load-generating tests. Version remains `0.6.5-rc.1`; dynamic quota remains opt-in; stable release is **NO-GO** until every gate has qualifying runtime evidence and independent review. A green generic CI run, a sealed protocol, or a collector's `COMPLETE` status is never a gate PASS.

## Before any state-changing or load-generating run

An authorized repository owner/operator must approve the host and maintenance window, confirm the source revision is on `main` with a clean tracked tree, identify the operator and reviewer, and create new evidence paths. Do not provision a runner, set approval variables, dispatch the approved workflow, change quota, start workload, force PSI, run rollback, or start soak without that authorization. Keep credentials/private config out of shared artifacts.

The approved runtime workflow is **Actions → Approved controller runtime (manual only) → Run workflow → `main`**. Its job condition requires both repository variables to equal the literal string `true`:

- `RUN_APPROVED_CONTROLLER_INTEGRATION`
- `APPROVED_CONTROLLER_RUNTIME_APPROVED`

It also requires a dedicated registered runner labelled `self-hosted`, `linux`, `x64`, and `lwg-approved-controller-test`. The runner must be isolated from production workloads. Before that job becomes eligible, a hosted policy-preflight uses the read-only repository secret `RUNTIME_ENVIRONMENT_POLICY_TOKEN` to verify the Environment has required reviewers with self-review disabled and an exact `main`-only deployment branch policy. The token must have only repository Administration read permission; missing/expired/insufficient credentials fail closed. The Environment's own required-reviewer gate still protects the runtime job. The job preflight rejects anything other than Ubuntu 22.04, cgroup v2 with the CPU controller, and a functioning user systemd manager. Missing prerequisites mean **OPEN / NOT RUN**; do not enable the variables merely to make the job start.

Each workflow attempt writes to `benchmarks/results/approved-runtime-<run-id>-<attempt>/`. The directory is create-only. If directory creation fails, the finalizer refuses to touch or upload the colliding path, avoiding stale-artifact misattribution. Step output is retained as `controller-step.log` and `routing-step.log`; each routing suite also gets a separate log and exit-status row so an early failure cannot silently skip the remaining suites. The finalizer records run/source/host/step outcomes, rejects symlinks and special files, writes `SHA256SUMS.txt`, verifies it, records `manifest-digest.txt`, and leaves the decision `OPEN_PENDING_INDEPENDENT_REVIEW_AND_EXTERNAL_DIGEST_RETENTION`. The digest appears in the GitHub job summary but must also be retained in the review/ticket system independently of the artifact. The repository currently has no `approved-controller-runtime` Environment; before enabling either repository variable, the owner must create it with required reviewers and an exact `main`-only deployment branch policy, and configure the read-only policy-token secret. Upload retention is 90 days. Workflow success does not itself close any gate.

## ABBA commands (G3/G4)

Run these only after owner approval on the declared independent host. Replace every placeholder with a real identifier and a fresh unique path; do not copy fixture values. The preregistration CLI refuses to create a protocol unless both explicit confirmations are supplied, the tracked tree is clean, and cgroup v2 CPU support is observed:

```sh
python3 benchmarks/preregister_abba.py create \
  --output "benchmarks/results/abba-<UTC>-<host-id>-sealed" \
  --host-id "<independent-host-inventory-id>" \
  --operator-id "<approved-ticket-or-operator-id>" \
  --workload-kind terminal-build \
  --confirm-independent-host --confirm-approved-window
python3 benchmarks/preregister_abba.py verify "benchmarks/results/abba-<UTC>-<host-id>-sealed"
```

Retain the printed `protocol_sha256` outside the run bundle before starting block A. For each block use a different, non-existing `RESULT` path and the same declared workload. The fixed block weights are A=20, B=80, B2=80, A2=20:

```sh
PREREG="benchmarks/results/abba-<UTC>-<host-id>-sealed"
OUT="benchmarks/results/abba-<UTC>-<host-id>"
mkdir -m 700 "$OUT"  # create once; choose a unique path that does not exist
# Repeat the command once per block, with the matching block and weight.
BENCH_REQUIRE_PREREGISTRATION=1 BENCH_PREREGISTRATION_DIR="$PREREG" \
  BENCH_PREREGISTRATION_BLOCK=A BENCH_AGGREGATE_ROUTING=true \
  BENCH_AGGREGATE_SCOPE_WEIGHT=20 WORKLOAD_KIND=terminal-build \
  REPS=5 DURATION=30 WORKERS=2 RESULT="$OUT/weight20-blockA.tsv" \
  benchmarks/routing-contention-isolated.sh
```

Repeat with `BENCH_PREREGISTRATION_BLOCK=B` and weight `80`, then `B2` and weight `80`, then `A2` and weight `20`; use the exact filename/weight pairs `weight80-blockB.tsv`, `weight80-blockB2.tsv`, and `weight20-blockA2.tsv`. The A result must be `weight20-blockA.tsv`. Preserve each command's full stdout/stderr and exit status. Evaluate each result in **release-gate mode**, which refuses absent or invalid preregistration, with `python3 benchmarks/performance-review.py --require-preregistration "$OUT/<WEIGHT-BLOCK>.tsv"`; then analyze the full four-block set with:

```sh
python3 benchmarks/analyze-aggregate-routing.py --require-preregistration \
  --out "$OUT/aggregate-pairs.tsv" --summary "$OUT/aggregate-summary.txt" \
  "$OUT/weight20-blockA.tsv" "$OUT/weight80-blockB.tsv" \
  "$OUT/weight80-blockB2.tsv" "$OUT/weight20-blockA2.tsv"
```

The result/evaluator tools use create-only output paths. `--require-preregistration` requires all four blocks to verify against the same sealed protocol digest, source revision, host and workload, in A/B/B2/A2 order, with matching filename and effective CPUWeight. Descriptive mode remains available for historical artifacts, but is not sufficient for G3/G4. An evaluator PASS is workload-scoped and still needs independent review. Preserve all adverse and confounded samples; do not rerun only unfavorable blocks or edit the sealed protocol.

## Evidence and release decision rules

1. Every attempt has a new run/attempt path. Existing paths, dangling symlinks, symlinks or non-regular entries inside an evidence bundle, missing inputs, failed checksums and incomplete telemetry are errors, not invitations to overwrite or infer success. Passive PSI collection is COMPLETE only if service PID/restart continuity and finite effective quota readbacks are intact; `REVIEW_REQUIRED` additionally requires a nearby exact-unit controller decision whose logged old/new quota agrees with readbacks around that decision.
2. Verify each bundle with its recorded SHA-256 manifest; record the manifest digest in the independent ticket/review system. A manifest detects drift only if its digest is retained separately.
3. Keep the runtime workflow's `OPEN_PENDING_INDEPENDENT_REVIEW_AND_EXTERNAL_DIGEST_RETENTION` decision. Reviewers must be independent of the operator who ran the test and must record gate ID, reviewed commit, host identity, artifact URL/path, manifest digest, raw-evidence findings, decision, reviewer identity and timestamp. The GitHub job summary is a separate record from the uploaded artifact, but the workflow cannot confirm a digest was copied to the independent review/ticket system.
4. `PASS` requires all gate-specific conditions above and traceable independent review. `FAIL`, `SKIP`, `NOT RUN`, `INCOMPLETE`, missing artifact, timeout, or review pending leaves the gate OPEN for release purposes.
5. Generic CI validates repository code and regression tests only. It cannot close G1–G7. Do not change the `0.90` throughput floor, `1.10` latency/work ceilings, PSI confounder rules, quota bounds or opt-in defaults to obtain a passing result.
6. Do not create `v1.0.0` while any mandatory gate is OPEN. If infrastructure or authorization is absent, leave the gate OPEN and wait for the exact owner/reviewer action above.
